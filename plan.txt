# PHASE 1 IMPLEMENTATION PLAN
# Floor-Plan-Aware Multi-Camera Global ID Tracking

Repository:
https://github.com/busoft-yuvaraj/multi-camera-person-reid

============================================================
OBJECTIVE
============================================================

Implement PHASE 1 of the multi-camera tracking system.

The ONLY objective of Phase 1 is:

    Maintain a stable Global ID for a person across:
    

        PANTRY
        PASSAGE
        WAITING LOBBY / ENTRY-EXIT

using:

    1. Local tracking
    2. Camera/zone information
    3. Spatial information
    4. Transition events
    5. Temporal/journey information
    6. Qdrant-based ReID search
    7. OSNet embeddings
    8. Existing PAR/Pose information where already available
    9. Multi-frame confirmation

Phase 1 MUST NOT implement violation/non-violation logic.

Phase 1 MUST NOT determine whether the person actually washed
their hands.

Phase 1 MUST only collect the events and journey metadata required
for Phase 2.

============================================================

============================================================

First inspect the entire existing repository before modifying it.

Do NOT rewrite the existing architecture unnecessarily.

Reuse existing implementations where possible.

Important existing components include:

============================================================
CRITICAL ARCHITECTURAL CHANGE
============================================================

CURRENT CONCEPT:

    New track
        ↓
    ReID comparison
        ↓
    Global ID

NEW CONCEPT:

    New local track
        ↓
    Identify camera
        ↓
    Identify logical zone
        ↓
    Detect transition/ROI events
        ↓
    Find spatially possible Global IDs
        ↓
    Find temporally possible Global IDs
        ↓
    Apply camera topology constraints
        ↓
    Query Qdrant ONLY for valid candidate Global IDs
        ↓
    ReID / PAR / Pose comparison
        ↓
    Multi-frame confirmation
        ↓
    Global ID assignment
        ↓
    Update journey metadata

DO NOT compare every new person against every Global ID.

Spatial + temporal + topology information must reduce the
candidate set BEFORE ReID matching.

============================================================
1. FLOOR PLAN
============================================================

There are three logical zones:

    PANTRY
    PASSAGE
    WAITING_LOBBY

Floor-plan relationship:

    WAITING LOBBY / ENTRY-EXIT
              |
              |
           PANTRY
              |
              |
           PASSAGE

The physical layout allows movement in multiple directions.

Do NOT assume a single fixed direction.

The topology must be configurable.

3. PANTRY ROI
============================================================

VERY IMPORTANT:

For Phase 1, the Pantry camera should use ONLY the previously
marked SINK AREA as the meaningful ROI.

Do NOT use the entire Pantry as the handwashing ROI.

The Pantry configuration must contain:

    pantry.sink

The system should detect:

    ROI_ENTER
    ROI_EXIT

Example:

{
    "event": "ROI_ENTER",
    "camera_id": "pantry",
    "roi_id": "sink",
    "local_track_id": 8,
    "timestamp": 124.5
}

IMPORTANT:

Do NOT convert ROI entry into a handwashing decision.

DO NOT create:

    handwash = true
    handwash = false

Phase 1 only records:

    person entered sink ROI
    person exited sink ROI

Handwashing interpretation belongs to Phase 2.

============================================================
4. TRANSITION LINES
============================================================

Current transition areas:

PANTRY:

    pantry_yellow
    pantry_green

WAITING LOBBY:

    lobby_exit

PASSAGE:

    passage_transition

Each transition must generate an event when a tracked person
crosses the line.

Use the bottom-center point of the person's bounding box.

Example:

bbox = (x1, y1, x2, y2)

foot_point:

    x = (x1 + x2) / 2
    y = y2

Determine:

    previous side of line
    current side of line

A transition event occurs when the person actually moves from
one side to the other.

DO NOT trigger a transition from a single noisy frame.

Use:

    multi-frame confirmation
    minimum movement
    debounce/cooldown

Example event:

{
    "event": "TRANSITION_CROSSED",

    "global_id": "Person_012",

    "camera_id": "pantry",

    "zone": "pantry",

    "local_track_id": 8,

    "transition_id": "pantry_yellow",

    "timestamp": 124.52,

    "direction": "A_TO_B"
}

5. CAMERA TOPOLOGY
============================================================

Create a configurable topology.

Example:

topology:

  pantry:
    next_zones:
      - waiting_lobby
      - passage

  waiting_lobby:
    next_zones:
      - pantry
      - passage

  passage:
    next_zones:
      - pantry
      - waiting_lobby

Do not hard-code these relationships in the matcher.

The topology exists to reject impossible candidate Global IDs.

Later, transition-specific topology can be added.

Example:

transition_rules:

  - from_camera: "pantry"
    transition: "pantry_yellow"
    candidate_zones:
      - "waiting_lobby"

  - from_camera: "pantry"
    transition: "pantry_green"
    candidate_zones:
      - "passage"

The architecture must support this even if the exact mapping
is tuned later using the actual CCTV videos.

============================================================

Add configurable temporal constraints.

Example:

temporal_constraints:

  pantry_to_waiting_lobby:
    min_seconds: 0.5
    max_seconds: 15.0

  waiting_lobby_to_pantry:
    min_seconds: 0.5
    max_seconds: 15.0

  pantry_to_passage:
    min_seconds: 0.5
    max_seconds: 15.0

  passage_to_pantry:
    min_seconds: 0.5
    max_seconds: 15.0

  waiting_lobby_to_passage:
    min_seconds: 0.5
    max_seconds: 15.0

  passage_to_waiting_lobby:
    min_seconds: 0.5
    max_seconds: 15.0

These values are initial values only.

They must be tuned against the real CCTV videos.

Do NOT hard-code them.

Example:

Global ID 12:

    last_seen_camera = pantry
    last_seen_timestamp = 100.0

New person:

    camera = passage
    timestamp = 104.0

delta = 4 seconds

If Pantry -> Passage allows 0.5-15 seconds:

    temporally valid

If delta = 60 seconds:

    reject or heavily penalize the candidate.

============================================================
11. SPATIAL GATING
============================================================

Before ReID:

Determine whether a Global ID is spatially compatible.

Use:

    current camera
    current zone
    previous camera
    previous zone
    transition crossed
    transition direction

Example:

New track:

    camera = passage

Candidate:

    G12
    last camera = pantry
    last transition = pantry_yellow

If Pantry -> Passage is valid:

    G12 = spatial candidate

Candidate:

    G50
    last camera = unrelated zone

If topology says the transition is impossible:

    G50 = reject

============================================================
13. QDRANT
============================================================

The existing repository already has Qdrant gallery support.

Reuse it.

However, change its role.

CURRENT:

    Qdrant mainly stores embeddings
    Python loads identities
    Python loops through identities
    Python calculates similarity

NEW:

    Qdrant performs candidate-restricted vector search.

Pipeline:

    spatial/temporal candidate IDs
            |
            v
    Qdrant filtered vector search
            |
            v
    top-K embedding matches
            |
            v
    group results by global_id
            |
            v
    identity-level ReID score

Example:

Candidate Global IDs:

    [G12, G18, G21]

Qdrant should search only those identities.

Do NOT search all identities.

============================================================
17. REID MATCHING
============================================================

ReID should be used AFTER candidate filtering.

Example:

Spatial candidates:

    G12
    G18

Temporal candidates:

    G12
    G18

Qdrant:

    G12 = 0.78
    G18 = 0.61

Then:

    G12 = candidate match

Do not let a Global ID with a high ReID score bypass
spatial/temporal constraints.

Example:

    G99 ReID = 0.91

but:

    G99 was last seen in an impossible camera/location

Then:

    G99 MUST NOT be selected.

============================================================
20. PENDING / AMBIGUOUS
============================================================

Do NOT immediately assign a Global ID when evidence is weak.

Use:

    PENDING
    AMBIGUOUS

Example:

    G12 = 0.67
    G18 = 0.65

Difference is too small.

Result:

    PENDING

Wait for additional evidence:

    next frame
    better ReID crop
    transition event
    stronger temporal evidence
    stronger spatial evidence

Only confirm when sufficient evidence exists.

21. EXISTING HYSTERESIS
============================================================

Reuse the existing hysteresis logic.

Do not remove it.

New logic:

    Spatial/Temporal candidate
        ↓
    Qdrant/ReID
        ↓
    candidate score
        ↓

        ↓
    confirmation
        ↓
    Global ID

Do not allow a single frame to cause a Global ID switch.

============================================================
22. GLOBAL ID SWITCHING
============================================================

This is one of the most important requirements.

Once a Global ID is CONFIRMED:

DO NOT immediately switch it because another ReID candidate
has a slightly higher score.

A switch should require:

    strong ReID evidence
    AND
    valid spatial transition
    AND
    valid temporal relationship
    AND
    multi-frame confirmation

If evidence is ambiguous:

    keep existing Global ID
    mark association as uncertain
    wait for more evidence

Protect journey integrity.

============================================================
23. GLOBAL ID REACQUISITION
============================================================

When a local track disappears:

DO NOT immediately create a new Global ID.

Example:

G12:

    last camera = pantry
    last seen = 100 sec

Track disappears.

State:

    TEMPORARILY_LOST

New track:

    camera = passage
    timestamp = 104 sec

If:

    topology valid
    temporal window valid
    Qdrant/ReID similarity valid

then:

    REACQUIRE G12

not:

    create G13

============================================================
FINAL RULE
============================================================

The most important architectural rule is:

    DO NOT ASK REID FIRST.

Instead ask:

    1. Where was this person?
    2. Which zone were they in?
    3. Which transition did they cross?
    4. Which cameras can they realistically appear on?
    5. How much time passed?
    6. Which Global IDs are therefore possible?
    7. Among those candidates, which one matches visually?
    8. Can the match be confirmed across multiple observations?
    9. Update the Global ID journey.

The system should use:

    FLOOR PLAN
        +
    SPATIAL CONSTRAINTS
        +
    TEMPORAL CONSTRAINTS
        +
    TRANSITION EVENTS
        +
    QDRANT / REID
        +
    MULTI-FRAME CONFIRMATION

to maintain Global IDs.

PHASE 2 will consume the resulting journey and determine:

    VIOLATION
    or
    NON-VIOLATION

Do not implement Phase 2 now.
